# GitHub-through-Supabase recovery bridge

This is the emergency source-recovery path for BKTSTR when an agent cannot reach GitHub directly. Normal development remains GitHub feature branch -> CI -> main -> Railway. The bridge only mirrors the public repository source; it is not part of the trading API.

Apply `ops/supabase/github_bridge.sql` once through the Supabase migration interface. The helper functions are intentionally not executable by anonymous/authenticated API roles; use the trusted Supabase SQL connection.

## Phase 1 - enqueue commit

```sql
select *
from public.bktstr_github_enqueue_commit('M00SEDR0iD', 'bktstr', 'main');
```

Keep the returned `snapshot_id` and `request_id`. Poll the existing pg_net response rather than resubmitting:

```sql
select id, status_code, content
from net._http_response
where id = <commit_request_id>;
```

## Phase 2 - enqueue tree

After the commit response is HTTP 200:

```sql
select public.bktstr_github_enqueue_tree('<snapshot_id>'::uuid) as tree_request_id;
```

Poll that exact request ID in `net._http_response`. When it is HTTP 200, the snapshot row contains the exact `git_commit` and `tree_sha`.

## Phase 3 - enqueue blobs

```sql
select public.bktstr_github_enqueue_blobs('<snapshot_id>'::uuid) as enqueued_blob_count;
```

This parses the recursive tree once and enqueues raw-content requests in one database call. Commit/tree discovery uses the GitHub REST API, while file bodies use `raw.githubusercontent.com` so a normal BKTSTR source tree does not exhaust GitHub's unauthenticated REST quota. Generated `__pycache__`, `.pyc/.pyo`, and `.pytest_cache` artifacts are excluded. Request IDs, paths, and Git blob SHAs are stored in `bktstr_repo_blob_requests`. Do not issue duplicate requests manually.

Check progress:

```sql
select
  count(*) as total,
  count(r.id) as responses_ready
from public.bktstr_repo_blob_requests b
left join net._http_response r on r.id = b.request_id
where b.snapshot_id = '<snapshot_id>'::uuid;
```

## Phase 4 - collect blobs

When responses are arriving, collection is idempotent and may be called repeatedly:

```sql
select *
from public.bktstr_github_collect_blobs('<snapshot_id>'::uuid);
```

A complete result reports `pending=0` and `failed=0`; the snapshot status becomes `complete`. Source file bodies are stored as UTF-8 bytes encoded into `content_base64`. The bridge is intended for the BKTSTR text/source tree; generated bytecode/cache artifacts are excluded and arbitrary binary-asset recovery is not a v0.3.5 guarantee.

Inspect the snapshot:

```sql
select snapshot_id, git_commit, status, created_at, completed_at
from public.bktstr_repo_snapshots
where snapshot_id = '<snapshot_id>'::uuid;

select path, blob_sha, encoding, byte_size, content_base64
from public.bktstr_repo_files
where snapshot_id = '<snapshot_id>'::uuid
order by path;
```

To reconstruct locally, base64-decode each `content_base64` value to its `path`. The GitHub blob SHA remains alongside every file for integrity verification.

## Failure handling

Never resubmit a request just because `net._http_response` is temporarily empty. Poll the stored request ID first. If GitHub returns a non-200 response, the corresponding helper raises with the HTTP status. The bridge never accepts an arbitrary outbound host; URLs are fixed to `https://api.github.com/repos/` and owner/repo/ref components are restricted to safe path characters.
