# BKTSTR v0.6 API-First Research Design

**Status:** Approved design; implementation has not started.

**Target release:** v0.6.0

**Foundation:** BKTSTR v0.5.0 strategy-neutral core.

## Purpose

Make REST the durable product interface for external programmatic research
clients. A future MCP server may expose the same high-level service functions,
but it is an optional adapter and must not introduce agent-specific behavior
into the HTTP API.

The API supports a natural research loop:

```text
baseline backtest -> parameter sweep -> compare variants
-> compare periods or regimes -> inspect trades -> form hypothesis -> repeat
```

## Goals

- Replace the hand-written HTTP surface with a typed FastAPI application and a
  complete generated `/openapi.json` contract.
- Keep HTTP routes thin and keep research logic outside of route handlers.
- Offer high-level research operations rather than a large CRUD-style surface.
- Create a durable, reproducible experiment record for every research
  operation, whether it completes inline or is queued.
- Keep the v0.5 immutable strategy, variable, measurement, provenance, and
  execution contracts authoritative.
- Authenticate external clients initially with one service-level bearer key.

## Non-goals

- MCP server implementation or agent-specific API logic.
- User accounts, per-client keys, or multi-tenant authorization.
- A web UI, React application, database-hosted portfolio product, or custom
  strategy code execution.
- Replacing v0.5 formula, data trust, execution, or public-result semantics.
- A Postgres/Supabase experiment store in this release.

## Architectural boundaries

```text
FastAPI routers and schemas
          |
          v
services/backtest.py      typed backtest orchestration
services/data.py          provider selection, normalized data, provenance
services/experiments.py   lifecycle, durable records, queue boundary
services/regimes.py       typed regime and context resolution
          |
          v
immutable v0.5 strategy / variable / measurement / execution core
```

Routes authenticate, validate typed models, select an execution mode, and
delegate. Services do not accept HTTP request or response objects. The existing
core does not import FastAPI, route, authentication, or storage-framework
types.

## Shared experiment envelope

Every submitted operation creates an `ExperimentRecord`. The envelope is a
shared lifecycle and reproducibility contract, not a generic operation payload.
Each operation still has its own strongly typed request and result models.

```json
{
  "experiment_id": "exp_01...",
  "operation": "backtest",
  "status": "queued",
  "created_at": "2026-08-25T15:40:31Z",
  "started_at": null,
  "completed_at": null,
  "execution": "auto",
  "request": {},
  "result": null,
  "error": null,
  "provenance": {}
}
```

`request` is the canonical serialization of the operation's typed request
model. `result` is the canonical serialization of its typed result model after
completion. Neither field accepts arbitrary, unvalidated client JSON.

`status` transitions only as follows:

```text
queued -> running -> completed
                 -> failed
```

Completed records are immutable. Retrying creates a new record with a link to
the original experiment rather than mutating history.

## REST surface

All `/api/v1/*` routes require the service bearer key unless stated otherwise.

| Route | Contract | Completion |
| --- | --- | --- |
| `GET /api/v1/health` | Lightweight liveness and build identity; unauthenticated. | `200` |
| `GET /api/v1/capabilities` | Registered strategies, request limits, data sources, regime fields, execution policy, and build/API versions. | `200` |
| `POST /api/v1/backtests` | One typed baseline/configured backtest. | `200` completed or `202` queued |
| `GET /api/v1/backtests/{id}` | Convenience typed view of one backtest experiment. | `200` |
| `POST /api/v1/parameter-sweeps` | Typed bounded parameter grid and objective. | Usually `202` |
| `POST /api/v1/compare` | Typed named variants or completed experiment IDs. | Usually `202` |
| `POST /api/v1/regime-comparison` | Typed periods or regime slices for the same configuration. | Usually `202` |
| `GET /api/v1/experiments/{id}` | Canonical shared experiment envelope. | `200` |
| `GET /api/v1/market-data` | Read-only normalized market-data inspection, with pagination. | `200` |

Routes express high-level research operations. There are no endpoints for
executing client-supplied formulas, mutating immutable strategy definitions, or
writing agent-specific hypotheses.

## Execution policy

Every submitted operation accepts:

```json
{ "execution": "auto" }
```

- `auto` is the default. Ordinary bounded backtests complete inline; configured
  cost limits queue expensive work.
- `sync` asks for immediate execution. If the operation cannot safely run
  inline, the service returns `409 execution_not_available` rather than
  silently changing the requested mode.
- `async` persists and queues the operation immediately.

Single `POST /api/v1/backtests` requests normally return `200 OK` with a
completed experiment and full result. Parameter sweeps, large comparisons, and
multi-symbol or multi-regime requests normally return `202 Accepted` with a
queued experiment ID. The job boundary exists from the first release, so an
operation can later move from inline to queued execution without changing the
research model or response envelope.

## Typed research contracts

The backtest request permits only a registered strategy reference and typed
configuration. It never accepts executable user code or arbitrary formulas.

```json
{
  "strategy": {
    "id": "bktstr.bearish-regime-scalp",
    "version": "1.0.0",
    "parameters": { "stop_pct": 1.0, "target_pct": 3.0 }
  },
  "market": {
    "symbol": "NVDA",
    "start": "2025-01-01",
    "end": "2025-12-31",
    "timeframe": "5m",
    "source": "auto"
  },
  "regime": { "enabled": true, "benchmark": "SPY" },
  "execution": "auto",
  "include_trades": true
}
```

A completed typed `BacktestResult` includes:

- headline P&L and return;
- EV per trade, win rate, profit factor, maximum drawdown, Sharpe ratio, and
  trade count;
- every trade's entry and exit timestamps, entry and exit prices, holding time,
  realized P&L, MFE, MAE, entry signal values, and applicable regime variables;
- the canonical strategy, market, regime, and execution configuration used;
- data source, data version, coverage, strategy version, execution-model
  version, BKTSTR version and commit, and experiment ID.

`ParameterSweepRequest` has a typed parameter grid and objective.
`CompareRequest` accepts named typed variants or completed experiment IDs.
`RegimeComparisonRequest` accepts explicit labeled periods or regime slices.
Their results are operation-specific typed models embedded in the same shared
experiment envelope.

## Reproducibility and Railway-volume persistence

`services/experiments.py` owns a durable experiment store on the Railway
volume:

- a SQLite index stores IDs, operation, lifecycle state, timestamps, and lookup
  fields;
- each experiment has canonical request, result, and provenance artifacts;
- writes and lifecycle transitions are atomic;
- retries create linked records instead of overwriting results;
- the storage interface is private and can later gain a Postgres/Supabase
  implementation without changing public experiment IDs or API schemas.

Every completed record preserves the exact strategy configuration, date range,
symbol, timeframe, data source and version, slippage and execution assumptions,
regime settings, software version and commit, and relevant coverage/provenance.
This data is sufficient to reproduce the original research operation and to
identify a changed input or runtime when reproduction differs.

## Authentication, errors, and discovery

One service-level bearer key protects the versioned API:

```text
Authorization: Bearer <BKTSTR_API_KEY>
```

`GET /api/v1/health` remains unauthenticated. Authentication stays in the HTTP
layer and is not passed into research services.

Every public success and failure is a typed model in generated OpenAPI. Errors
use one stable envelope:

```json
{
  "error": {
    "code": "execution_not_available",
    "message": "This operation cannot run synchronously.",
    "details": {},
    "request_id": "req_01..."
  }
}
```

Validation failures retain field paths. Provider, storage, execution-policy,
authentication, and experiment-state failures receive stable machine-readable
codes.

`GET /api/v1/capabilities` exposes registered strategies and versions,
available data sources, supported regime fields, accepted limits, current
execution policy, and API/build identities. It publishes no agent-specific
logic.

Mutating submissions accept an idempotency key. Reusing the same key with the
same canonical typed request returns the existing experiment. Reusing it with a
different request is rejected with a stable conflict error.

## Legacy compatibility

The existing `GET /api/v1/backtest` may remain temporarily only as a thin
adapter over `services/backtest.py`. It must emit deprecation metadata and a
migration link, and it must not preserve a separate request-validation or
execution path. If the adapter would require disproportionate rework or test
burden, v0.6 removes it explicitly with a documented migration response.

## Verification requirements

- OpenAPI contract tests cover all routes, models, enums, auth requirements,
  and error envelopes.
- Service tests prove formula and execution parity independently of HTTP.
- Experiment tests cover canonical persistence, immutable completed records,
  provenance completeness, idempotency, retries, and lifecycle transitions.
- API tests cover inline and queued execution, polling, parameter sweeps,
  comparisons, regime comparisons, and paginated market-data inspection.
- Compatibility tests either prove the legacy adapter delegates to the new
  service or prove its documented removal behavior.
- Production acceptance tests exercise the released FastAPI health,
  capabilities, and a representative completed backtest.

## Future adapters

A future MCP server maps tool calls to the same typed service functions and
schemas. It neither owns experiment lifecycle nor creates a parallel product
contract. A future web UI consumes the same REST endpoints and OpenAPI models.
